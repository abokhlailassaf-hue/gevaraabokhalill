# سيرفر الديوان العسكري — بناء جديد كامل

## ما تغيّر عن السيرفر القديم

تم حذف كل ما هو غير ضروري: لا Supabase، لا نظامي تخزين مزدوجين (dual backend)،
لا SSE (بث إشعار فقط ثم طلب جلب منفصل)، لا استطلاع دوري (polling) لا في
الإرسال ولا في الاستقبال. النظام الآن مكوّن ذاتياً بالكامل (self-contained):

| المشكلة التي ذكرتها | الحل هنا |
|---|---|
| التعديلات ترجع للنسخة الأصلية بعد التحديث | تخزين دائم فعلي في SQLite على قرص، لا "لقطة قديمة" يمكن أن تكتب فوق تعديل حديث — كل مفتاح له رقم مراجعة يزيد فقط |
| مزامنة فورية عند تعديل جهاز لبقية الأجهزة | اتصال WebSocket دائم؛ أي تعديل يُرسل خلال أجزاء من الثانية ويُبث فوراً لكل الأجهزة المتصلة |
| حفظ دائم لأي تعديل مهما كان | كل تعديل يُكتب على القرص (WAL + synchronous=FULL) **قبل** إرسال أي رد، ويُسجَّل أيضاً بشكل دائم لا يُحذف في جدول `history` — راجع `/api/history/:key` |

الأهم: **لم يتم تعديل `index.html` نفسه إطلاقاً**. الصفحة كانت مبنية أصلاً
بخطافات جاهزة (`window.Five66Sync`, `_setPendingSyncState`, `_getPendingSyncState`,
`window.Five66State`) — الملف الجديد `public/sync-v2.js` يتصل بها مباشرة.

## هيكل المشروع

```
five66-server/
├── server.js          # Express + WebSocket، مصادقة، كل نقاط الـ API
├── db.js               # SQLite (better-sqlite3): تخزين + سجل تاريخي دائم
├── package.json
├── .env.example
├── data/                # (محلياً فقط) — على Railway يجب أن يكون هذا Volume دائم
└── public/
    ├── index.html       # واجهة التطبيق كما هي، دون أي تعديل
    ├── sync-v2.js        # محرك المزامنة الفوري الجديد (الجزء الأهم)
    ├── manifest.json     # placeholder بسيط (لم يكن مرفوعاً)
    ├── persons-photos.json    # placeholder فارغ {} (لم يكن مرفوعاً)
    └── shamcash-photos.json   # placeholder فارغ {} (لم يكن مرفوعاً)
```

**ملاحظة:** `archive-ledger.js` (يوفر `window.Five66Archive` لسجل التراجع/الأرشفة)
كان مرجّعاً في `index.html` لكنه لم يُرفع لي، فهو غير موجود هنا. الصفحة تتعامل
معه بأمان إن لم يوجد (`if (window.Five66Archive)`), فلا يكسر شيئاً، لكن ميزة
الأرشفة تلك لن تعمل حتى ترفع الملف الحقيقي إلى `public/archive-ledger.js`.
كذلك `persons-photos.json` و`shamcash-photos.json` هنا فارغان — إن كانت عندك
نسخ فعلية بصور محفوظة سابقاً، استبدل الملفين بهما قبل النشر.

## ⚠️ الخطوة الأهم على Railway: Volume دائم

هذا هو السبب شبه المؤكد وراء "رجوع البيانات بعد كل تحديث" سابقاً: قرص Railway
المحلي **مؤقت** ويُمسح عند كل Deploy جديد، ما لم يكن المسار داخل Volume دائم.

خطوات الإعداد:
1. من لوحة تحكم Railway → مشروعك → تبويب **Volumes** → أنشئ Volume جديد.
2. اربطه بالخدمة (service) على مسار مثلاً `/data`.
3. في **Variables** أضف: `DATA_DIR=/data`.
4. أضف أيضاً `BASIC_AUTH_USER` و`BASIC_AUTH_PASSWORD` (أو `BASIC_AUTH_USERS_JSON`).

بدون هذه الخطوة سيعمل كل شيء بشكل طبيعي بين الأجهزة أثناء تشغيل نفس النسخة،
لكن أي Deploy جديد سيمسح `data/five66.db` وتعود الصفحة لبيانات فارغة/افتراضية.

## ✅ قائمة تحقق سريعة للنشر على Railway

1. ارفع محتوى هذا المجلد إلى مستودع Git (GitHub) واربطه بخدمة جديدة على Railway،
   أو استخدم `railway up` من سطر الأوامر مباشرة من هذا المجلد.
2. **Volumes** → أنشئ Volume جديد واربطه بالخدمة على المسار `/data`.
3. **Variables** أضف:
   - `DATA_DIR=/data`
   - `BASIC_AUTH_USER` و`BASIC_AUTH_PASSWORD` (أو `BASIC_AUTH_USERS_JSON`)
4. لا حاجة لضبط `PORT` — Railway يضبطه تلقائياً والسيرفر يقرأه من `process.env.PORT`.
5. ملف `railway.json` المرفق يضبط فحص الصحة على `/healthz` (نقطة بدون مصادقة
   حتى لا يفشل الفحص بسبب Basic Auth) وسياسة إعادة التشغيل عند الفشل.
6. بعد أول Deploy ناجح، افتح رابط الخدمة — سيطلب المتصفح بيانات الدخول (Basic Auth).
7. تحقق من `GET /api/sync-status` بعد الدخول للتأكد أن `persistentDiskConfigured: true`.

## التشغيل محلياً

```bash
npm install
cp .env.example .env   # ثم عدّل القيم داخله
npm start
```

افتح `http://localhost:3000` (سيطلب المتصفح بيانات الدخول Basic Auth).

## نقاط الـ API

- `GET /api/state` — كامل الحالة الحالية (مفتاح ← نص JSON)، للتوافق فقط.
- `POST /api/sync/push` — رفع تعديلات عبر REST (احتياطي؛ WebSocket هو المسار الأساسي).
- `GET /api/history/:key?limit=20` — آخر نسخ محفوظة لمفتاح معيّن (استرجاع يدوي عند الحاجة).
- `GET /api/sync-status` — حالة التخزين، عدد الأجهزة المتصلة الآن.
- `GET /api/backup` — نسخة احتياطية كاملة قابلة للتنزيل.
- WebSocket على نفس المنفذ (`/`) — القناة الفعلية للمزامنة الفورية.

## كيف تعمل المزامنة الفورية

1. عند فتح الصفحة، يتصل `sync-v2.js` عبر WebSocket ويستقبل فوراً كامل الحالة
   الحالية من السيرفر (`welcome`)، ويعيد رسم كل الأقسام.
2. عند أي تعديل محلي (`saveState()` الموجودة أصلاً في الصفحة)، يُجدوَل رفع خلال
   350 ملّي ثانية فقط (لتجميع كتابة متتالية سريعة دون فقد الفورية الفعلية) عبر
   نفس اتصال WebSocket.
3. السيرفر يكتب على القرص **أولاً** (بشكل ذري داخل معاملة واحدة)، ثم يبث
   التحديث فوراً لكل الأجهزة الأخرى المتصلة.
4. أي جهاز آخر يستقبل التحديث خلال أجزاء من الثانية ويطبّقه على واجهته مباشرة
   دون إعادة تحميل الصفحة.
5. إذا انقطع اتصال WebSocket مؤقتاً، يُعاد الاتصال تلقائياً (backoff تصاعدي)،
   ويُستخدم `POST /api/sync/push` كاحتياطي مؤقت حتى لا يضيع أي تعديل.
